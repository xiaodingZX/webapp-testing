# 通用配置项探索测试工作流

## 输入与运行目录

从上下文提取目标 URL、登录方式、测试环境、目标页面、已知业务规则和本次授权。默认策略为“可逆写入”；用户已声明“每次执行默认授权新建、保存、修改、删除等操作”时，测试环境运行策略设为 `authorized_all_actions`。运行目录优先使用 `WEBAPP_TESTING_ARTIFACT_ROOT\<YYYYMMDD-HHmmss>-<page-slug>\`；未设置该环境变量时，使用当前工作区的 `artifacts\webapp-testing\<YYYYMMDD-HHmmss>-<page-slug>\`。

创建运行目录、`screenshots\` 和运行清单后开始测试。运行清单、文件名和报告不得包含密码、Cookie、令牌或其他凭证。截图按用户授权保留原始页面数据，仅保存在本地运行目录。

## 页面发现与配置项清单

1. 打开目标页面，保存初始 DOM 快照和首屏截图。
2. 遍历当前页面可达的路由、页签、折叠区、弹窗、抽屉、表单、列表、筛选、确认框和页面专有组件，形成页面能力表。基于实际 DOM、语义角色和可访问名称发现能力，不预置业务模块、字段名、路由或页面功能。
3. 逐项枚举页面可见模块、页签、筛选组、列表列、按钮、开关、弹窗、抽屉和表单字段；每个可见项必须进入 `configurationInventory`，或记录不可达、跳过、阻塞或未验证原因。
4. 旧报告、旧截图或旧 `case-results.json` 只能作为参考证据。仅当确认同一目标页面、同一测试范围、逐项配置清单完整、逐项证据完整时，才允许复用旧产物中的结论；复用时仍必须重新核对当前页面可见项。
5. 对每个表单、弹窗、抽屉或可编辑配置容器建立 `formContext`。它由页面路径、容器语义路径和进入方式组成；进入方式从可见入口推断为新建、编辑、复制或未知。
6. 在每个 `formContext` 中枚举可操作或具有状态的配置项。使用 `页面路径 + 容器路径 + 可访问名称 + 控件角色或类型 + 序号` 生成 `configurationId`，避免同名控件冲突。
7. 为每个配置项记录：`configurationId`、所属可见模块、`formContext`、`containerPath`、可访问名称、控件类型、初始可见和可用状态、值状态摘要、可选项摘要、已见校验提示、依赖来源、可达性、覆盖状态、用例引用或未覆盖原因。值状态仅使用空值、有值、已选、未选或未知等摘要，不写入原始值或 DOM。
8. 识别开关、单选、下拉、页签和折叠区导致的显示、隐藏、启用、禁用关系。每次只改变一个可逆条件，比较配置项清单的差异并记录依赖边，再恢复基线后继续探索。需要多个条件同时满足且没有明确安全路径的配置项标记为未验证或阻塞，不构造组合穷举。
9. 新建、编辑和复制入口形成独立 `formContext`。配置项的初始状态、可用性或可选项有差异时分别覆盖；完全一致时仍验证编辑态预填和取消恢复。

## 动态用例矩阵

1. 按唯一动作和状态划分等价类，不按每条业务记录重复执行。每个页签、唯一操作图标和独立筛选组至少覆盖一次；在 `authorized_all_actions` 下，每个持久化字段和每个可见选项均需独立完成保存闭环，不能以代表性状态或选项替代。搜索覆盖命中、无结果和恢复。
2. 每个发现的配置项必须关联至少一个独立用例，或标记为阻塞、跳过、失败或未验证并写明原因。持久化字段的关联用例必须记录基线、目标状态、保存提交、持久化复核、恢复提交和恢复复核；操作控件按自身语义记录覆盖维度。
3. 配置项粒度门禁：
   - 生成用例前必须先完成 `configurationInventory`。新建入口、编辑入口、配置页面、弹窗整体、抽屉整体、表单整体或页面模块整体不得作为唯一配置项记录。
   - 入口类能力只能作为页面能力或入口用例。进入表单、弹窗或抽屉后，必须继续拆分其中所有可见、可输入、可选择、可切换、可展开或可触发依赖变化的配置项。
   - 每个配置项必须有唯一 `configurationId`、所属可见模块、`formContext`、`containerPath`、`controlType`、初始状态、覆盖状态、`coverageCaseIds` 或 `coverageReason`。
   - `coverageStatus` 为 `covered` 时必须有关联用例和证据；`coverageStatus` 为 `blocked`、`skipped` 或 `unverified` 时必须有 `coverageReason`。
   - 如果只验证了入口或页面可见性，配置项状态只能标记为 `unverified` 或 `blocked`，不能标记为 `covered`。
   - `configurationInventory` 为空、明显少于页面可见项、只覆盖代表性流程或由旧用例、旧截图反推生成时，必须在 `blockers` 中标记“不满足完整颗粒度”，不能交付为完成。
4. 按控件类型生成配置项用例：
   - 开关、复选框：逐项反转当前状态，保存并重新读取页面复核，再恢复初始状态、保存并再次复核。
   - 单选、下拉、多选：每个可见选项单独作为配置项，逐项选择目标选项，保存并重新读取页面复核，再恢复初始选择集合、保存并再次复核；不构造多个选项或多个字段的组合穷举。
   - 文本、数字、日期、文本域：逐字段临时输入代表性有效值，保存并重新读取页面复核，再恢复。页面明确显示必填、格式、范围或掩码约束时，额外验证可见反馈；输入或失焦可能自动保存时按自动保存闭环执行。
   - 上传、下载、导出：默认验证入口、页面已见限制或确认界面后取消；在 `authorized_all_actions` 下仍只在可恢复且不会产生外部文件、外部发送或不可逆覆盖时提交。否则记录阻塞原因。
   - 可编辑表格或复杂组件：按行内开关、输入框、选择器和操作按钮拆分；持久化字段逐项保存复核恢复，操作按钮按自身语义验证。
   - 禁用或隐藏控件：通过已发现的单一可逆依赖条件验证显示、隐藏、启用或禁用变化并恢复。
5. 配置项用例拆分采用最小独立交互单元：
   - 文本、数字、时间、日期和文本域：独立生成输入与恢复用例。
   - 开关、复选框和单选：独立生成状态切换与恢复用例。
   - 下拉、多选和选择器：独立生成展开、选择代表值与恢复用例。
   - 富文本和话术编辑器：独立生成编辑入口、临时输入风险判断与取消恢复用例。
   - 可编辑表格：按行内开关、输入框、选择器和操作按钮分别生成配置项。
   - 依赖配置：每次只改变一个前置条件，记录显示、隐藏、启用或禁用变化。
   - 保存或确定：关联已复核的持久化写入；取消：修改后取消并重新打开验证基线未持久化；入口：验证可达性和目标容器打开，不能作为字段保存覆盖。
   - 删除、导出、上传和发送：未授权时仅生成入口和取消用例；`authorized_all_actions` 下仅在测试数据、清理方式和恢复路径可确认时执行完整流程。
6. 配置项与真实执行用例采用多对多映射：
   - 一个配置项可以关联一个或多个执行用例。
   - 一个执行用例可以覆盖多个配置项。
   - 报告展示按配置项拆行，执行过程按业务流程复用；复用用例必须为每个关联配置项分别记录基线、目标状态、保存复核和恢复复核，不能以一次代表性保存覆盖同组其他项。
   - `configurationInventory` 是配置项覆盖台账，`cases` 是真实执行流程；必须通过 `coverageCaseIds` 关联，不能用配置项清单替代执行结果。
   - 判断配置项是否实际覆盖时，同时查看 `coverageStatus`、`coverageCaseIds`、关联 `cases[].status`、`cases[].coverage`、`cases[].actualResult`、`cases[].restoration` 和证据。
7. 同一 `formContext` 下的多个配置项必须通过 `id + label + controlType + containerPath` 区分。未实际交互验证的配置项不能只因页面可见、首屏截图可见或入口可点击就标记为完整覆盖；只能标记为 `unverified`，或在 `coverageReason` 中明确说明仅完成可见性、入口或初始状态覆盖。
8. 页面实际发现新建、编辑、复制、删除或批量操作入口时，生成相应用例。新建、编辑和复制进入对应表单上下文后按配置项规则测试；删除和批量删除默认验证代表性数据选择、确认界面、取消和选择状态恢复。缺少明确需求依据时，确认框缺失归入待产品确认项。
9. 为每条用例记录页面能力、配置项标识、风险类型、前置条件、操作步骤、预期依据、断言、恢复动作和证据文件名。页面已有文案可作为界面预期，不能替代未提供的业务规则。

## 执行与恢复

- **只读**：导航、页签、查看、搜索、筛选、分页、打开确认框。直接执行，并恢复筛选、页签或路由。
- **可逆写入**：临时输入、开关切换、可恢复排序或状态。操作前记录基线；确认测试环境且不存在潜在外部发送影响后执行；立即恢复并重新读取页面验证。
- **提交写入和破坏性操作**：保存、新建、删除、发送、导出、上传或自动保存风险操作。默认只验证入口、表单和确认框，随后取消。用户明确提供一次性测试数据、写入授权和清理方案后才执行完整流程。

对每个持久化字段或选项型配置项，按“基线、单项修改、保存、重新打开相同 `formContext` 或刷新复核、恢复基线、保存、再次复核”执行。自动保存控件省略保存点击，但保留两次刷新或重新进入复核。取消操作按“临时修改、取消、重新打开、确认基线未持久化”执行。若恢复失败、出现验证码、会话失效、未知确认弹窗或无法判断外部影响，停止同一 `formContext` 的后续写操作，记录当前页面、截图和阻塞原因。

## 浏览器证据与报告

遵循 `browser:control-in-app-browser`。先获取 DOM 快照，再使用 data-testid、语义化角色或可访问名称定位元素；每个状态变化、错误、确认框、路由变化和恢复结果保存截图。

使用 Codex Browser 的 `tab.screenshot()` 获取 PNG 字节，并使用 Node 的 `fs.writeFile()` 写入 `screenshots\`。文件名采用 `<序号>-<case-id>-<状态>.png`，例如 `003-CFG-TOGGLE-restore.png`。在 `case-results.json` 使用相对路径引用证据。

每个配置项用例必须有至少一个证据引用；可见性可复用首屏或表单截图，写入验证必须为每个配置项保存基线、保存后复核和恢复后复核的独立证据。报告默认以“配置项用例结果”为主视图，逐项列出验证类型、保存前状态、目标状态、保存后复核、恢复后复核、覆盖状态、关联执行用例、实际结果、恢复或清理结果、证据和未覆盖原因；执行流程用例作为审计明细保留。

写入最终 `case-results.json` 和 `report.md` 后，从 Skill 根目录运行 `node scripts/render-report.mjs <run-directory>` 生成 `report.html`。HTML 使用内置 CSS、相对截图路径和结构化结果；不加载网络字体、脚本或其他外部资源。渲染失败时记录为报告生成阻塞，不能声称 HTML 报告已生成。

## 断言与定性

每个用例独立记录以下层次：页面可见状态、路由结果、网络响应或后端持久化结果、恢复结果和未验证项。页面可见通过不能证明业务已生效。

将可复现页面错误、路由失败、明确状态不一致和与已提供需求冲突的行为记录为“已确认缺陷”。缺少需求依据的文案、计数和交互一致性观察记录为“待产品确认项”。

## 结束条件

当所有唯一能力类别和所有发现的配置项均已覆盖，或已有明确未覆盖原因时结束。`authorized_all_actions` 运行中，所有可写配置项必须具有完整保存闭环，或有明确 `failed`、`blocked` 原因；存在 `unverified`、`skipped`、代表性保存或缺失复核的可写项时，必须标记“不满足完整颗粒度”。连续两轮探索没有发现新能力或配置项时结束探索。验证所有可逆操作均已恢复，再写入 Markdown、结构化结果和 HTML 报告；运行失败时仍写入已完成用例、证据和阻塞信息。
