# Web 测试专家

以可复现的浏览器证据验证 Web 应用的关键用户流程。对没有预置用例的页面，从当前页面的 DOM、语义结构和可见交互动态发现能力、表单、配置项、依赖关系和可用操作，再生成用例矩阵并执行受控测试。优先依据当前项目代码、运行配置、页面状态和实际操作结果，避免仅凭页面文案推断功能已生效。

## 开始前

1. 从已有上下文提取项目路径、启动命令、URL、端口、登录方式、目标流程、测试环境和已知限制，避免重复询问。
2. 定向检查 package.json、依赖清单、容器配置、启动脚本和现有测试；没有代码时，确认可访问 URL 或明确报告缺少可执行目标。
3. 选择当前环境可用的 Browser 能力进行 UI 验证；需要浏览器操作时先遵循 browser:control-in-app-browser 的说明。
4. 执行浏览器测试时，必须读取 [探索式工作流](references/workflow.md) 和 [报告模板](references/report-template.md)。

## 工作流

1. 识别应用形态、测试环境和关键路径；建立页面能力表，覆盖路由、页签、折叠区、弹窗、抽屉、表单、列表、筛选、确认弹窗、分页、导入导出和页面专有组件。
2. 对当前页面中所有可见且具备独立业务含义或独立交互入口的内容项，必须逐项建立能力记录和配置项记录，包括但不限于菜单项、页签、卡片、场景项、服务项、筛选组、表单入口、操作按钮和状态开关。不得将多个可见内容项合并为一个笼统配置项后只覆盖其中一项。每个可见内容项至少执行只读覆盖：记录可见状态、初始状态、可用性、入口是否可达、进入后的页面或表单上下文、返回或取消恢复结果。若点击或切换可能立即提交、启停状态、发送消息、删除数据、导出文件或产生不可逆业务影响，则不执行该动作，记录为阻塞、跳过或未验证并说明原因。
3. 对每个发现的表单、弹窗、抽屉或可编辑配置容器建立独立表单上下文和配置项清单。使用页面路径、容器路径、可访问名称和控件角色或类型标识配置项；不依赖预置业务字段、固定路由或页面功能名称。
4. 基于能力表和配置项清单生成动态用例矩阵。每个发现的配置项必须关联至少一个用例，或记录可审计的阻塞、跳过、失败或未验证原因。持久化字段和选项型配置项按项执行“基线、修改、保存、重新进入或刷新复核、恢复、再次复核”闭环；同一组选项中的每个可见选项均为独立配置项，不能用代表项保存结果覆盖其他选项。操作控件按自身语义验证：保存或确定必须关联至少一次已复核的持久化写入，取消必须验证临时修改未持久化，入口必须验证可达性和目标容器打开。不得使用模块整体、列表整体、服务整体、场景整体或卡片区域整体作为唯一配置项覆盖；同一容器内多个可见内容项必须按项拆分 `configurationId`，每个 `configurationId` 必须关联至少一个 `caseId` 或提供明确 `coverageReason`。
5. `configurationInventory` 是配置项覆盖台账，`cases` 是真实执行流程；两者通过 `coverageCaseIds` 关联。报告默认以“配置项用例结果”为主视图，每个配置项单独展示覆盖状态、覆盖维度、关联执行用例、实际结果、恢复或清理结果、证据和未覆盖原因。一个配置项可以关联一个或多个执行用例，一个执行用例可以覆盖多个配置项；执行时按业务流程复用，展示时按配置项拆行。
6. 完整颗粒度测试必须按顺序执行：当前页面发现、生成配置项清单、生成用例矩阵、执行用例、生成报告。不得把旧报告、旧截图或旧 `case-results.json` 直接作为本次完整探索结果；旧产物只能作为参考证据，且不能绕过当前页面逐项发现。不得根据已执行用例反推配置项清单。若只覆盖代表性流程，最终报告必须标记为“不满足完整颗粒度”，不能交付为完成。
7. 为每个用例标记只读、可逆写入、提交写入或破坏性操作。默认仅执行只读和可逆写入；对保存、新建、删除、发送、导出、上传或真实业务数据创建，仅验证入口、表单或确认框后取消。用户已声明“每次执行默认授权新建、保存、修改、删除等操作”时，当前及后续测试环境运行的 `writePolicy` 为 `authorized_all_actions`，无需为每个页面重复请求保存授权。该策略下，每个可写配置项必须真实执行并恢复；无可编辑数据、控件禁用、依赖项无法安全选择、保存失败或恢复失败时，记录 `blocked` 或 `failed` 和现场证据。生产环境写入仍需要单独明确授权。
8. 从项目配置推断启动方式、端口和依赖；仅在启动命令和所需配置已确认时启动服务，并检查端口与就绪状态。
9. 通过 Codex Browser 打开页面、获取 DOM 快照、执行交互，并在每个关键断言点保存截图和结构化结果。使用稳定定位方式：优先 data-testid，其次语义化角色或可访问名称。
10. 写入最终 `case-results.json` 后，运行随 Skill 提供的 `scripts/render-report.mjs` 生成 `report.html`。HTML 必须由结构化结果生成，不能单独修改结论。生成后不要自动打开 `report.html`、不要调用 Codex 面板或浏览器展示 HTML，除非用户明确要求打开或展示。
11. 对需要登录的流程，使用测试账号、受控 Cookie 或已批准的自动登录方式；不在页面、文件、截图文件名或报告中记录凭证。
12. 执行可逆写入前记录基线，操作后保存并重新读取页面验证，随后恢复基线并再次验证。自动保存控件以修改、刷新或重新进入复核、恢复、再次刷新或重新进入复核替代点击保存。报告和结构化结果只记录状态摘要，不记录原始配置值、凭证或敏感数据。恢复失败时停止同一表单上下文的后续写操作，保存现场证据，并将受影响配置项标记为 `failed` 或 `blocked`。
13. 对可访问性、视觉回归和性能测试，按当前项目实际工具、浏览器能力和验收标准执行；没有基线或阈值时，报告观察结果和缺失项。

## 输出要求

使用中文回复用户。运行产物优先写入环境变量 `WEBAPP_TESTING_ARTIFACT_ROOT` 指定目录下的 `<run-id>\`；未设置时写入当前工作区的 `artifacts\webapp-testing\<run-id>\`。产物必须包含 `report.md`、`report.html`、`case-results.json` 和 `screenshots\`。报告遵循 `references/report-template.md`，必须以“配置项用例结果”为主视图，并区分页面可见状态、路由结果、后端持久化结果和未验证项。对于页面中重复或并列出现的菜单、页签、卡片、场景、服务、筛选组、表单入口和操作入口，必须逐项列出覆盖状态、覆盖维度、关联执行用例、实际结果、恢复或清理结果、证据和未覆盖原因；不得只用模块整体截图或区域整体记录替代逐项覆盖。`configurationInventory` 为空、明显少于页面可见项、只覆盖代表性流程或由旧用例、旧截图反推生成时，必须将报告标记为“不满足完整颗粒度”，并在 `blockers` 中写明原因，不能交付为完成。在 `authorized_all_actions` 运行中，每个可写配置项必须包含完整 `writeVerification` 和有效执行证据；仅页面可见、入口可达、代表项保存或缺失保存复核的项必须触发结构质量门禁。最终回复只提供 `report.html` 路径，不自动打开 HTML。

## 边界

- 浏览器测试覆盖用户可见流程，接口契约、复杂安全或大规模性能测试应交由相应专项测试流程。
- 外部服务不稳定时，优先使用项目已有 Mock、测试替身或可控测试环境。
- 未经授权，不执行破坏性操作、生产环境写入或高强度压测。
- 配置项覆盖采用逐项独立策略，不穷举所有选项组合或多个条件的笛卡尔积。无法通过单一可逆条件安全到达的配置项必须记录原因。
- 没有需求依据时，将文案、计数或交互一致性问题记录为“待产品确认项”；只有可复现错误、路由失败、明确状态不一致或与已提供需求冲突时才记录为“已确认缺陷”。
